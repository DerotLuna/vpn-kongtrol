# Executable egress and destination precedence

Sources accessed 2026-11-25.

- Linux routing policy can match the socket mark, look up the ordinary route table while suppressing default routes, and then look up an app-specific table. Kongtrol uses a suppression threshold of 1 to ignore both a default route and a pair of default halves. More-specific host routes, including LAN routes and existing policy destinations, remain available. [iproute2 rule manual](https://github.com/iproute2/iproute2/blob/main/man/man8/ip-rule.8.in)
- A WireGuard peer still needs allowed destinations even when its client skips installing routes. On Linux the private configuration uses `Table = off` and keeps peer AllowedIPs. Kongtrol leaves system DNS unchanged on this path. [wg-quick implementation](https://git.zx2c4.com/wireguard-tools/tree/src/wg-quick/linux.bash)
- On Windows the built-in per-app VPN API sets filters on Windows VPN platform profiles. Existing WireGuard/OpenVPN adapters in Kongtrol create other interfaces. The WFP redirect API for their flows is implemented by a kernel callout. A production kernel driver needs a signing and distribution path. [Microsoft VPN traffic filters](https://learn.microsoft.com/en-us/uwp/api/windows.networking.vpn.vpntrafficfilter?view=winrt-26100), [WFP redirection](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/using-bind-or-connect-redirection), [driver signing](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-reqs)
- A signed third-party WireGuard client was also considered. WireSock documents that its app list and IP ranges form an intersection. Substituting it would change the VPN backend and would still need independent routing of other applications to the same destination. [WireSock matching rules](https://wiresock.net/documentation/guide/using-allowedips-and-allowedapps)

Policy precedence is independent of executable names. In destination-first mode a program and a browser can both use the same explicit destination route. When the other profile's destination route disappears, the program uses its own connected executable profile for that destination. In app-first mode it uses its profile even if another destination route is available. The browser continues to use its own routing rules.

The first implementation applies exact executable file identities to new sockets and starts when a directly managed, single-peer, dual-stack WireGuard profile starts. Shared resolvers, inherited sockets, app replacement and third-party provider-owned tunnels have separate validation requirements. The privileged test creates a genuine Linux WireGuard interface in an isolated namespace and checks socket marking and route selection for TCP and UDP over IPv4 and IPv6. No external VPN server account or encrypted peer exchange was used. Windows and macOS activation are unavailable with this back end. See [ADR-0111](../adr/0111-activate-linux-executable-egress.md).
