# Research: landing load performance (headers, caching, render-blocking CSS, main thread)

Version 1.0.0 · 2026-11-18

## Question

Live findings on https://kongtrol.app (PageSpeed mobile 98 / Best Practices 92, Cloudflare
speed test mobile 90 with TBT 280 ms): an unrecognized `Permissions-Policy` feature, hashed
assets served with `max-age=0`, three render-blocking stylesheets, a forced reflow, six
non-composited animations and one long main-thread task. What do the standards and vendor docs
say, and which fix measures best?

## Findings

- **Cloudflare `_headers` [1].** Default for static assets: `Cache-Control: public, max-age=0,
  must-revalidate` plus an `ETag` (hash of the file). "Headers defined in the `_headers` file
  override what Cloudflare ordinarily sends." A request matching several rules inherits all of
  them; the same header twice is joined with a comma (so two `Cache-Control` rules conflict) and
  `! Header` removes only what earlier rules added. One splat per pattern, 100 rules, 2,000
  characters per line. `_headers` does not apply to responses generated by Worker code; this
  site has no Worker script, so it applies to every response.
- **Immutable [2][3].** `immutable` tells the client the body will not change while fresh, so it
  skips revalidation on reload; correct only for URLs whose content never changes (hashed names).
  Stable URLs need a finite `max-age` and ETag revalidation.
- **`interest-cohort` [4].** FLoC was withdrawn by Google (replaced by Topics); Chrome no longer
  recognises the token and logs "Unrecognized feature: 'interest-cohort'" (seen live). Removing it
  changes nothing for visitors.
- **Render-blocking CSS [5][6][8].** Stylesheets in `<head>` block the first paint until they are
  downloaded. Options: inline the critical CSS and load the rest without blocking [6]; tools such
  as Beasties inline the rules matching the document and defer the rest — its `media`/`swap`
  strategies use an `onload` attribute and `js` an injected script (blocked by our CSP without
  `'unsafe-hashes'`/new hashes); `body` moves the full stylesheet to the end of `<body>` (no JS),
  which still downloads and re-applies the whole CSS after first paint (reasoned, not measured).
  Matching is against the document, not the viewport [8], and our HTML is the whole prerendered
  page, so almost every rule would be inlined anyway. Merging the two CSS files with `cssCodeSplit: false` [7] still leaves one
  blocking request. Inlining the whole page CSS (~15 KB gzip) removes every blocking request at
  the cost of no cross-page CSS cache.
- **Fonts [7][14].** Importing `fonts.css` through Vite resolves its `url()`s, so the woff2 files
  get content hashes (immutable-cacheable) and the `@font-face` rules ship inside the inlined CSS.
  `woff2` files are 13–85 KB, above `assetsInlineLimit` (4 KB), so they are never turned into
  `data:` URIs (which `font-src 'self'` would block). Preloads keep `crossorigin`.
- **Forced reflow [9].** Reading geometry (`getBoundingClientRect`, `offsetHeight`, `scrollY`,
  `innerHeight`, …) after a DOM/style write forces a synchronous layout; reads must be batched
  before writes. A `ResizeObserver` delivers sizes after layout without forcing one.
- **Non-composited animations [10][11].** Only `transform` and `opacity` animate on the
  compositor; `color`, `background`, `border-color`, `background-position`, `stroke-dashoffset`
  need style + paint on the main thread every frame. Lighthouse listed (local run, mobile `/`):
  `atShield` (color), `atDot` ×2 (background), `atBtn` (background/color/border), `atCheck`
  (stroke-dashoffset), `sbRowFlow` (background-position) and the switchboard rows' color/border
  transitions, which ran during load because the board rotated off screen.
- **Long task [12][13].** React 18 hydrates content inside `<Suspense>` boundaries separately,
  "with tiny gaps in which the browser can handle events", and hydrates first the part the user
  interacts with [12]. With `renderToString` and nothing suspending, the server HTML is the same.
  A boundary that receives new props before it hydrates is client-rendered instead (React logs
  "This Suspense boundary received an update before it finished hydrating") — the boundaries'
  elements must be stable (memoized).
- Local trace (Chrome, 4× CPU, home page): the main thread was dominated by Style & Layout
  (several full-page layouts: initial, each font swap, hydration) and by a 1 s interval that
  re-rendered the whole hero to tick the uptime. Results are noisy on this machine (other
  Lighthouse/Chrome processes ran in parallel), so before/after runs were interleaved.
