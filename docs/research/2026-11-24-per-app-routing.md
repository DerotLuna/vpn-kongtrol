# Routing executables and their subprocesses by VPN profile

Version 1.2.0 · 2026-11-24

## What the roadmap asks for

The current delivery covers direct assignment by executable. Inheritance is deferred. The rest of this note records the findings for both modes. [GitHub issue #64](https://github.com/DerotLuna/vpn-kongtrol/issues/64)

Assign an executable to a profile for all of its outbound traffic, including traffic from the subprocesses it launches. For example, in Windows, assign `Orca.exe` and a terminal it starts to profile A, and an independently launched `claude.exe` to profile B. The same executable can therefore have a different path depending on how its instance was launched. Programs outside those rules use destination and default routing. Sending both program trees to the same IP tests that the executable or process instance actually determines the path. [Issue #64](https://github.com/DerotLuna/vpn-kongtrol/issues/64)

Profile `priority` orders competing rules after Kongtrol has a policy input. An executable assignment requires the system routing implementation to obtain that input for the connection and apply the selected profile. A route learned from DNS or from a blocked connection applies to every caller of the destination once installed in the shared route table.

Kongtrol stores application patterns, and the policy engine resolves them to a profile for diagnostics. The route resolver installs destination routes and updates WireGuard peer AllowedIPs. The monitor samples TCP connections and checks their destination against those policies. Application identity needs to reach the point where the OS selects an egress. [Policy engine](../../internal/policy/engine.go), [route resolver](../../internal/monitor/policyresolver.go), [policy monitor](../../internal/monitor/policywatch.go)

## Optional inheritance

Propose a per-rule choice between **only this program** and **also programs it launches**. The first applies to each instance matching the selected executable. Each different executable it starts gets its own explicit rule, if any, or normal destination/default routing. The second passes the assignment to new children and grandchildren. A separately started instance of the same child executable keeps its own assignment or normal routing. Propose that an explicit rule on a child selects that child's profile and whether inheritance continues through its branch. For example, a Claude instance with its own rule uses Claude's profile when started from Orca, and if Claude's inheritance is off, its descendants return to normal routing unless they match an explicit rule. This precedence is proposed and needs product confirmation before implementation.

Match by verified executable path or OS app identity, and track the lifetime of each process instance. Use metadata available before its first connection. Polling for new processes leaves a gap. Preserve associations after the parent exits while its children are still running. Define the behavior for sockets created before a rule is enabled, sockets inherited from another process, and rule changes to an active program. Live transfer of existing flows is **no verificado**.

The scope includes connections created by the executable and the descendants covered by the rule. Shared DNS services, requests sent to an already-running browser, and other OS brokers can create their own sockets. Process ancestry alone cannot associate those connections with a caller. For Orca, also distinguish a Windows-native shell from a command running in WSL 2. WSL 2 runs a Linux kernel in a VM, so Windows executable inheritance does not establish which Linux process owns the connection, including in mirrored networking. These are separate acceptance cases for any promise covering all traffic. [Mullvad IPC and DNS limits](https://github.com/mullvad/mullvadvpn-app/blob/main/docs/split-tunneling.md), [WSL architecture](https://learn.microsoft.com/en-us/windows/wsl/compare-versions), [WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking)

## Platform findings

- **Linux.** Launch selected applications inside a cgroup v2 before they open sockets. The kernel can classify traffic by socket cgroup in nftables, set a packet mark, and select a separate IPv4 or IPv6 routing table for each profile via the routing policy database. Mullvad's documentation illustrates app exclusion from one tunnel. The proposed Kongtrol prototype would select among multiple profile tables. Verify source-address selection and return traffic since output re-routing may occur after the socket selected a source address. WireGuard network namespaces are a second option for a launch-only prototype with isolated routes. Moving a tunnel interface into a namespace also changes where Kongtrol can observe and use it for ordinary destination policies. [nftables manual](https://netfilter.org/projects/nftables/manpage.html), [iproute2 rule manual](https://github.com/iproute2/iproute2/blob/main/man/man8/ip-rule.8.in), [Mullvad split-tunnel design](https://github.com/mullvad/mullvadvpn-app/blob/main/docs/split-tunneling.md), [WireGuard namespaces](https://www.wireguard.com/netns/)
- **Windows.** WFP supports application-aware filtering and offers callouts at the bind and connect layers. Microsoft documents bind redirection for changing the local address and connect redirection for handing a flow to a proxy. Mullvad ships a driver for splitting traffic between its tunnel and the normal network. Kongtrol still needs to demonstrate interface selection across two tunnels and coexistence with other clients' WFP rules. A user-mode block plus a global route learned from the blocked destination leaves shared-IP conflicts unresolved on every retry. Windows VPNv2 also has per-app configuration in its own VPN profiles. Compatibility with arbitrary provider interfaces is **no verificado**. A driver requires a Microsoft signing and distribution path, and Microsoft's attestation page documents EV prerequisites and Windows Update limitations. [WFP redirection](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/using-bind-or-connect-redirection), [Mullvad driver](https://github.com/mullvad/win-split-tunnel), [VPNv2 CSP](https://learn.microsoft.com/en-us/windows/client-management/mdm/vpnv2-csp), [Microsoft attestation](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-attestation)
- **macOS.** Apple documents per-app VPN for managed configurations. For desktop distribution, a Network Extension transparent proxy can select TCP and UDP flows by originating app and open outbound connections through a selected path if the OS and client permit it. The provider needs the Network Extension entitlement and suitable packaging. Its DNS settings are ignored, so the prototype would need to verify the system DNS path separately. Selection of two existing VPN interfaces and coexistence with provider extensions are **no verificado**. [Apple VPN routing](https://developer.apple.com/documentation/networkextension/routing-your-vpn-network-traffic), [flow copying](https://developer.apple.com/documentation/networkextension/handling-flow-copying), [transparent proxy behavior](https://developer.apple.com/documentation/networkextension/netransparentproxyprovider), [provider deployment](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment)

All external sources accessed 2026-11-24.

### Windows

Both modes can use the same design. Match the executable's full path on process creation, then attach the route choice to the connection's owning process. Apply a direct match in both modes. Copy the assignment to a newly created process only when the selected branch allows inheritance. Microsoft distinguishes the recorded parent from the actual process creator. A prototype must define which relationship follows the user's intent and test launches through Windows brokers separately. WFP supplies process path and ID to a callout at layers where those metadata fields are present. Mullvad's driver documents synchronous classification, child propagation, dynamic reconfiguration and blocking unwanted established flows. It demonstrates nearly the same identity and inheritance primitives for a tunnel exclusion. Selection among Kongtrol profiles and a per-rule inheritance toggle are implementation work. [Windows creation metadata](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_ps_create_notify_info), [WFP flow metadata](https://learn.microsoft.com/en-us/windows/win32/api/fwpsu/ns-fwpsu-fwps_incoming_metadata_values0), [Mullvad driver](https://github.com/mullvad/win-split-tunnel)

Job Objects can help group an explicitly launched Windows process and its children, with documented exceptions. A job membership does not select a VPN. A user-mode policy for blocking by executable can protect or diagnose, while real redirection needs another mechanism. In the WFP callout design, test a local-address change and traffic verification on the expected interface. If a local proxy is used for TCP/UDP instead, test its outbound sockets with an explicit interface and verify UDP semantics separately. Production also requires confirming Microsoft's driver signing and distribution route. [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [WFP redirection](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/using-bind-or-connect-redirection), [Winsock interface selection](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ip-socket-options), [Microsoft signing options](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/driver-signing-offerings)

### Linux

Inheritance on is a natural fit for a launcher with cgroup v2. Children start in the parent's cgroup and retain membership through exec. A WireGuard network namespace has a comparable inheritance model for newly started processes. Both mechanisms group descendants automatically. For inheritance off, a classifier must distinguish the selected executable from a different executable launched in the same group. Validate an executable-aware mechanism that assigns the route before socket or flow setup, for example using supported kernel hooks, with checks for fork/exec, scripts and interpreters, programs launched normally from the desktop, and already-open sockets. Watching exec from user space and moving processes after the notification can race the first connection. Socket classification and transparent launch coverage for this mode are **no verificado**. [Kernel cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html), [nftables sockets](https://netfilter.org/projects/nftables/manpage.html), [WireGuard namespaces](https://www.wireguard.com/netns/)

**Observed locally on 2026-11-24.** In Ubuntu 24.04 under WSL 2, a shell launched with a systemd user scope, its child after exec, and its grandchild after exec all reported the same scope via `/proc/.../cgroup`. The independent shell reported a different group. This exercised process grouping only. No VPN or network routes were changed. [systemd scope](https://www.freedesktop.org/software/systemd/man/latest/systemd.scope.html)

**Executable-only prototype.** A cgroup socket-create program reads the current executable's inode and device from the running kernel's BTF layout, and looks up those fields with the current UID. A matching entry sets the socket mark before route selection. A child that opens its own socket after exec is classified independently. Linux policy routing uses the mark to select a dedicated table, with a terminal unreachable route if the interface disappears. [Linux cgroup socket verifier and context access](https://github.com/torvalds/linux/blob/master/net/core/filter.c), [Cilium eBPF](https://github.com/cilium/ebpf), [classifier](../../internal/privops/app_classifier_linux.go), [route table](../../internal/privops/app_route_linux.go)

In a fresh WSL 2 network namespace, the test captured IPv4 UDP packets sent by three different executables to the same IP and port on three separate virtual Ethernet paths. Two had dedicated rules and the third used the main table. Removing one selected interface made its destination unreachable for the marked app. The other two could still send. A separate test confirmed that an unassigned executable launched by the selected program got an unmarked socket. The tests run on Linux with BPF and network administration capabilities using `KONGTROL_TEST_APP_CLASSIFIER=1 go test ./internal/privops -run TestAppClassifier -v`. The test uses synthetic interfaces. Integration with live VPN profiles, IPv6, TCP, DNS, already-open sockets and executable replacement are **no verificado**. [Integration tests](../../internal/privops/app_classifier_linux_test.go)

### macOS

For the direct mode, test a transparent proxy matching the source signing identifier and opening its outbound flow with a required network interface. Test whether the required VPN interface is available to the Network Extension for the selected profile. For inheritance, a signing identifier identifies the app opening a flow and carries no descendant relationship by itself. Correlate a process instance from the flow's optional audit token with a reliable process event stream. Endpoint Security exposes fork and exec events, with a separate entitlement and user approval such as Full Disk Access for a direct client. Mullvad's public source shows a different approach using Apple's `eslogger` for process events and BPF devices for traffic handling, with documented IPC limitations. Validate audit token availability and event ordering on the supported macOS versions before promising inherited assignment. [Flow metadata](https://developer.apple.com/documentation/networkextension/neflowmetadata), [required interface](https://developer.apple.com/documentation/network/nw_parameters_require_interface(_:_:)), [Endpoint Security events](https://developer.apple.com/documentation/endpointsecurity/event-types), [Endpoint Security permission](https://developer.apple.com/documentation/endpointsecurity/es_new_client(_:_:)), [Mullvad process tracking](https://github.com/mullvad/mullvadvpn-app/blob/main/talpid-core/src/split_tunnel/macos/process.rs), [Mullvad BPF](https://github.com/mullvad/mullvadvpn-app/blob/main/talpid-core/src/split_tunnel/macos/bpf.rs)

## What a shared-destination test proves

Use the same destination IP and port with the same transport in two independent program instances. Observe both VPN interfaces and the normal interface in the test environment. Using different destinations would allow an implementation that merely installs ordinary destination routes to pass. Two active profiles are useful as one regression test. A single active profile and the normal path also suffice for testing that a child process switches paths when inheritance changes. Tunnel captures or server-side observations should identify the test client independently of the UI.

Test both settings with the same child executable launched from Orca and separately. Add a grandchild, a child with its own rule, simultaneous startup and traffic, disconnect and reconnect, plus a run against IPv4 and IPv6 and TCP and UDP. DNS and delegated connections require their own test cases.

## Kongtrol requirements to validate

- Separate route tables and transport routing. For app-wide internet traffic the selected WireGuard peer must accept those destinations and the server must route them. Installing AllowedIPs for both default prefixes must not install two competing system defaults. Keep each tunnel's encrypted transport on an appropriate underlying route. [WireGuard routing](https://www.wireguard.com/netns/), [native default egress](../adr/0025-native-default-egress.md)
- Establish the precedence of app rules, destination rules and the default path before integrating with the policy engine. Validate how the kill switch and the profile's disconnect policy interact with flows from both apps when their destination is identical.
- Match the selected root executable by verified path or OS app identity. Track process instances and their descendants before they create connections. Test Orca launching a shell, the shell launching a network client, and a separate instance of that same client started outside Orca. Define the precedence when Orca launches an executable with its own explicit assignment, such as `claude.exe`. On Windows the process creation notification distinguishes the creator from the recorded parent. [Windows process creation metadata](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_ps_create_notify_info) (accessed 2026-11-24)
- Verify DNS separately. An app may delegate resolution to a shared system service, whose sockets belong to the service. Also test child processes, already-running instances, and relaunches that delegate to an existing process. Identify supported app launch paths in both the dashboard and the CLI. [systemd-resolved](https://www.freedesktop.org/software/systemd/man/latest/systemd-resolved.service.html)
- In attach mode, the provider controls its tunnel's permissions, DNS, routes and kill switch. Compatibility requires testing per provider and OS. [Provider attach mode](../adr/0006-provider-adapters-attach-mode.md)

The OS mechanisms and existing Kongtrol behavior were reviewed through documentation and source. Live multi-tunnel enforcement, rollback and provider compatibility are **no verificado**.
